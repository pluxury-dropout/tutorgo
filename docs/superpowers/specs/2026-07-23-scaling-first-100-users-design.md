# Готовность к первым 100 юзерам: ёмкость, тарифы, реплики

Дата: 2026-07-23
Статус: аудит + план, к исполнению по пунктам
Автор аудита: разбор кода main/2026-07-23

## Зачем этот документ

Ответ на вопрос «когда поднимать реплики и тарифы Supabase/Railway/Vercel/LiveKit
и как это понимать». Не абстрактно, а по цифрам из текущего кода. Держим рядом
как чеклист перед запуском и как карту потолков.

## Единица нагрузки — не «юзер», а одновременный урок

«100 юзеров» ≠ единица ёмкости. Считать надо в **одновременных уроках**.

100 репетиторов × ~5 уроков/день, сжатых в вечернее окно 16:00–20:00 →
**30–100 одновременных уроков** в пик.

Один урок стоит системе:
- 2 WS-соединения на доске (препод + ученик), хаб в памяти инстанса
- 2 участника LiveKit
- поток UPSERT'ов в `board_elements` (штрих = UPDATE своей строки)

Всё ниже посчитано на этой единице, не на «юзере».

## Что упрётся первым — в порядке наступления

### ① Supabase Storage — умрёт раньше всех, с запасом

`S3_ENDPOINT` смотрит в Supabase Storage. Туда же летят отрендеренные страницы
PDF: `worker/run.go` `renderDPI = 200`, JPEG q85. Лист A4 @200 DPI = 1654×2339 ≈
300–600 КБ. PDF на 30 страниц ≈ 15 МБ.

Free tier: 1 ГБ хранилища, 5 ГБ egress/мес.
→ **~60 импортированных PDF — и хранилище кончилось.** Egress выгорает за неделю
(каждый открывший доску тянет картинки заново). На 100 репетиторах — первая неделя.

**Рычаг сильнее любой оптимизации кода:** `renderDPI` 200 → 150. Пикселей меньше
в 1.8×, на экране разницы почти нет (150 DPI на A4 = 1754 px по высоте, с запасом
на зум ×1.5). Одна строка в `worker/run.go`, минус ~45% и хранилища, и трафика.

### ② Postgres, 500 МБ на free — второй в очереди

`board_elements` — строка на элемент, `data jsonb`. Freedraw-штрих с сотнями
точек = 2–8 КБ. Час активного рисования ≈ 200–500 элементов ≈ **1–3 МБ на
страницу доски**. Чистятся ТОЛЬКО tombstones старше суток
(`repository/whiteboard.go` `DeleteOldTombstones`), живые элементы лежат вечно.
Сотни досок × месяцы → сотни МБ.

Обратный отсчёт до потолка мерить руками раз в неделю:
`SELECT pg_total_relation_size('board_elements');`

### ③ Флаш-цикл доски — потолок в самом коде, ~50–100 активных досок

`handlers/board_buffer.go` `Run`: тик раз в секунду, и `flush` идёт
**последовательно по страницам** — `MergeElements` на каждую в отдельном
`SendBatch`. Один round-trip до Supabase ≈ 10 мс. 100 активных досок → флаш
занимает ~1 с, ровно упираясь в интервал тикера. За этой отметкой запись
отстаёт: рисование пиры видят мгновенно (рассылка раньше персиста), но при
обрыве/деплое теряется не «последняя секунда», а больше.

**Чинится НЕ репликами**, а склейкой всех страниц в ОДИН `pgx.Batch` — N
round-trip'ов схлопываются в один. ~5 строк. Не раньше, чем активных досок
станет за полсотни (см. счётчик в /health ниже).

### ④ LiveKit Cloud — самая дорогая статья, единственная линейная по минутам

`LIVEKIT_URL` = livekit.cloud. Free tier исчерпается на первых десятках уроков.
100 репетиторов × 20 уроков/мес × 60 мин × 2 участника = **240 000
участнико-минут/мес.** Это основная строка бюджета, не «потерпим». Считать по их
актуальному калькулятору — цифры у них менялись.

### ⑤ Railway — не упрётся

Go с 200 WS = сотни горутин и проценты ядра. Память — только там, где
`pdftoppm`: 200 DPI × `MaxWorkers: 2` (`worker/run.go`) = пики в сотни МБ. Роль
`worker` уже отделена — поэтому эти пики не роняют API. На 512 МБ коробке
однопроцессный режим OOM'ился бы на импорте.

### ⑥ Vercel — не упрётся вообще

72 из 89 компонентов — `use client`, SSR-фетчей нет, Next работает как CDN для
статики. Единственный расход — три прокси-роута в `frontend/src/app/api/`, из них
`room-status/[lessonId]` дёргается каждые 5 с ожидающим учеником.

Причём роут — passthrough на ПУБЛИЧНЫЙ эндпоинт бэкенда, адрес берёт из
`NEXT_PUBLIC_API_URL` (то есть ничего не скрывает). Браузер может ходить в Go
напрямую: минус invocation'ы, минус ~50 мс на хоп, минус файл.

## Когда поднимать реплики

**На 100 юзерах — НЕ поднимать.** Один процесс тянет, а вторая реплика прямо
сейчас **сломает доски**: `wbHub` живёт в памяти инстанса, broadcast идёт только
своим клиентам (`handlers/whiteboard_ws.go`). Двое на одной доске с разных реплик
не видят штрихов друг друга.

Реплики нужны не ради нагрузки, а ради **деплоя без разрыва уроков** — сейчас
каждый релиз рвёт все WS посреди занятия. Порядок жёсткий:

1. Пока можно деплоить ночью — одна реплика, и всё.
2. Когда «деплоить ночью» перестанет работать → СНАЧАЛА fan-out доски через Redis
   (publish `update` в `board:<pageID>`, каждый инстанс подписан на свои открытые
   хабы; cursor/viewport через Redis НЕ гнать), ПОТОМ replicas=2.
3. CPU-масштабирование — где-то после 500 одновременных уроков.

## Тарифы: что, когда, по какому сигналу

| Что | Когда | Сигнал |
|---|---|---|
| **Supabase Pro** | до первых реальных юзеров | арифметика: 1 ГБ storage = 60 PDF |
| **LiveKit** | как только уроки пойдут регулярно | дашборд участнико-минут |
| **Railway** | по факту, usage-based | RSS воркера в пиках импорта |
| **Vercel Hobby** | долго не понадобится | — |
| **Redis (Railway)** | вместе с replicas=2, не раньше | — |

## Наблюдаемость: чего не хватает, чтобы «понимать»

Сейчас `/health` (`main.go`) показывает только пул БД. Всё, что упирается первым,
не видно. Три счётчика закрывают вопрос:

- `len(m.hubs)` — активные доски (сигнал по ③: подходит к 50 — чинить флаш)
- суммарное число WS-клиентов — сколько народу реально на уроках
- `len(b.pending)` — если растёт между тиками, буфер уже отстаёт

Плюс `pg_total_relation_size('board_elements')` руками раз в неделю — отсчёт до
потолка БД (②).

## Порядок действий

1. `renderDPI` 200 → 150 — одна строка, минус ~45% storage и egress (①)
2. Три счётчика в /health — ~10 строк, без них следующее вслепую
3. Supabase Pro — до запуска, не по сигналу (①②)
4. Удалить прокси-роуты на Vercel, ходить в бэкенд напрямую (⑥)
5. Утечка в rate limiter: `middleware/rate_limit.go` map лимитеров никогда не
   чистится, новый IP оседает навсегда. Sweep-горутина на ~8 строк по образцу
   `service/calendar_cache.go` `sweepExpired`. Уже течёт при одной реплике.
6. Склейка флаша в один Batch (③) — по счётчику `len(m.hubs)` из п.2
7. Fan-out доски через Redis (см. «Когда поднимать реплики») — только под
   replicas=2

## Чего НЕ делать, хотя «во всех зрелых проектах есть»

- **Очередь на Redis** — River уже в Postgres, транзакционно с данными. Два
  брокера = два источника истины.
- **Сессии/refresh-токены в Redis** — им нужна ревокация и аудит, это БД, не
  хранилище с eviction.
- **Идемпотентность платежей в Redis** — сейчас через unique `order_id`
  (`InsertPendingPayment` claim). Redis может выселить ключ → двойное списание.
- **Distributed lock на фоновые job'ы** — не нужен: `AutoComplete` идемпотентен
  (`UPDATE … WHERE status='scheduled'`), `RenewDue` защищён claim-строкой. Лок с
  TTL добавил бы новый режим отказа. Исключение — goose при 2+ `ROLE=api`, там
  нужен **postgres advisory lock** (`main.go` уже это знает в докблоке
  `runMigrations`).
- **Кэшировать всё подряд** — на этом объёме индексный запрос к Postgres быстрее
  round-trip'а до Redis плюс сериализации.

## Смежный разбор: где ещё уместен Redis (не для ёмкости, для реплик)

Из того же аудита, актуально в момент replicas>1, не раньше:

- **Кэш состояния подписки** — `middleware.RequireActiveSubscription` делает
  `GetByTutor` на КАЖДЫЙ запрос auth-группы. Redis-кэш с TTL 30–60 с + drop на
  webhook/`RenewDue` (инвалидация на всех инстансах сразу, иначе юзер заплатил, а
  ему ещё минуту 402).
- **Инвалидация `calendarCache` через pub/sub** — не переносить кэш в Redis (в
  памяти быстрее), а разослать по шине «сбрось tutorID». На двух репликах мутация
  на A не сбрасывает кэш на B → до 60 с устаревшего календаря.
- **Видимость Redis** — `pubsub.New` не пингует при старте, `/health` про Redis
  не знает. Кривой `REDIS_URL`, который парсится, но не коннектится = воркер
  молча теряет события. Ping в `New` с Warn (не fatal) + строка в /health.
