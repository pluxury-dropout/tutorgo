# Доска: сервер как источник истины

Дата: 2026-07-20
Статус: дизайн согласован, к реализации
Ревизия: 2026-07-20 — добавлены `files`, порядок seq, флаш буфера на shutdown,
замер сида, фазы выката, advisory lock на goose

## Проблема

Сейчас доска устроена так: клиент — источник истины, сервер — ретранслятор и
хранилище BLOB'ов. Клиент раз в 3 секунды присылает **всю сцену целиком**, сервер
кладёт её в `board_pages.snapshot`.

Из этой модели следуют три тупика.

**1. Клиент может стереть доску.** 2026-07-20 в 14:30 страница `d4148093` была
перезаписана содержимым `{"elements":[],"files":{}}`. Причина: персист переехал с
WS на HTTP, а у WS была неявная защита — до открытия сокета отправить было
некуда. HTTP уходит всегда, и клиент успевал запостить пустую сцену
смонтированного Excalidraw до прихода сида. Точечный фикс (гейт `seededRef`)
сделан, но защищает лишь один из путей: модель «клиент присылает всё целиком»
позволяет стереть доску принципиально.

**2. Амплификация записи.** Стоимость сохранения пропорциональна размеру всего
документа, а не размеру изменения. Один штрих переписывает 500 КБ. На горизонте
50 одновременных уроков это ~1.3 МБ/с постоянной записи в WAL (после gzip), и
цена растёт по мере заполнения доски: конец урока дороже начала на порядок.

**3. Состояние комнаты в памяти процесса.** `hub.clients` живёт в одном инстансе.
`LISTEN/NOTIFY` используется только для доставки серверных событий (готовый PDF),
но не для рисования. Следствие: второй `ROLE=api` инстанс ломает доску — участники
на разных инстансах не видят друг друга. Значит невозможен ни горизонтальный
скейл, ни rolling deploy без разрыва урока.

## Требования

- Горизонт: до ~50 одновременных уроков (~150 WS-соединений).
- Идущий урок не должен замечать деплой.
- Потеря содержимого доски недопустима; потеря нескольких секунд рисования при
  сбое — допустима.
- Плавность рисования не должна ухудшиться; желательно улучшить.

## Решение

Сервер становится источником истины. Правило слияния Excalidraw переносится с
клиента на сервер и выражается в SQL.

### Ключевое наблюдение

У элементов Excalidraw уже есть `id`, `version` и `versionNonce`, и клиентский
`reconcileElements` сливает по правилу:

```
version больше              → принять
version меньше              → отклонить
version равна, nonce МЕНЬШЕ → принять
version равна, nonce больше → отклонить
```

Тай-брейк по **меньшему** `versionNonce` — проверено по исходникам Excalidraw
(`shouldDiscardRemoteElement`: «resolve conflicting edits deterministically by
taking the one with the lowest versionNonce»). Интуиция подсказывает обратное;
ошибка здесь даёт молчаливое расхождение сервера и клиентов.

Отдельная CRDT-библиотека не нужна: модель конфликт-резолюшна уже существует,
её достаточно перестать выбрасывать.

### Модель данных

```sql
CREATE TABLE board_elements (
    page_id    uuid NOT NULL REFERENCES board_pages(id) ON DELETE CASCADE,
    element_id text NOT NULL,
    version    int  NOT NULL,
    nonce      bigint NOT NULL,
    data       jsonb NOT NULL,
    updated_at timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (page_id, element_id)
) WITH (fillfactor = 80);

ALTER TABLE board_pages ADD COLUMN elements_migrated_at timestamptz;
ALTER TABLE board_pages ADD COLUMN files jsonb NOT NULL DEFAULT '{}'::jsonb;
```

`data` — jsonb, а не bytea+gzip: элементы мелкие, поэлементное сжатие почти
ничего не даёт, а jsonb оставляет возможность запросов по содержимому.

`fillfactor = 80` — таблица живёт под потоком UPDATE'ов одних и тех же строк.
Запас в странице даёт HOT-обновления: новая версия строки ложится рядом со
старой, индекс не трогается. Без этого каждый штрих плодит записи в первичном
индексе и работу автовакууму.

### Файлы

Снапшот — это не только `elements`. Второе поле, `files`, — карта
`fileId → {url, mimeType}`, указатели на S3 (`excalidrawSync.ts`,
`useExcalidrawSync.ts`). Поэлементная таблица его не покрывает: элемент типа
`image` несёт `fileId`, но не URL. Уронить `files` — значит превратить все
картинки и импортированные PDF-страницы в серые прямоугольники.

`files` живёт колонкой на `board_pages`, а не отдельной таблицей: записи
иммутабельны (загруженный файл не переписывается — новая картинка получает
новый `fileId`), поэтому конфликта нет по определению и слияние сводится к
`files = board_pages.files || $1`. Строки на элемент это не заслуживает.

Удаление осиротевших файлов не делаем: указатель весит десятки байт, а S3
чистится своей политикой. Если понадобится — та же фоновая задача, что чистит
tombstones.

Слияние — в `WHERE`-клаузе UPSERT'а, без блокировок и без чтения перед записью:

```sql
INSERT INTO board_elements (page_id, element_id, version, nonce, data)
VALUES (...)
ON CONFLICT (page_id, element_id) DO UPDATE
   SET version = EXCLUDED.version,
       nonce   = EXCLUDED.nonce,
       data    = EXCLUDED.data,
       updated_at = now()
 WHERE board_elements.version < EXCLUDED.version
    OR (board_elements.version = EXCLUDED.version
        AND board_elements.nonce > EXCLUDED.nonce)
```

Два инстанса могут писать один элемент одновременно — результат детерминирован
средствами Postgres.

### Поток данных

```
клиент A ведёт штрих
  │  update {elements:[…]}   ← формат сообщения не меняется
  ▼
инстанс 1
  ├─ Redis: INCR board:{pageId}:seq → PUBLISH board:{pageId}
  │                                      └→ инстанс 2 → его клиенты
  ├─ своим клиентам страницы
  └─ буфер UPSERT'ов → флаш раз в 1 с или на 200 элементах

новый клиент подключается
  ▼
ServeWS → SELECT data FROM board_elements WHERE page_id = $1
        → {type:'snapshot', elements:[…], seq: N}
```

Порядок важен: сначала рассылка пирам, потом запись в БД. Рисование не ждёт
Supabase, который находится в другой сети.

Сообщение из Redis несёт `origin` — UUID инстанса-отправителя; инстанс
отбрасывает собственное эхо.

### Порядок seq

`INCR` идёт **до** локальной рассылки, а не параллельно ей. Иначе свои же
клиенты получают сообщения в порядке, не согласованном с нумерацией, и просят
ресинк на ровном месте. Номер, присвоенный сообщению, один и тот же на локальном
пути и в публикации — рассылаем уже пронумерованное.

Цена — roundtrip в Redis в горячем пути. Он в приватной сети Railway (доли
миллисекунды против десятков до Supabase), поэтому терпимо. Без Redis
(`REDIS_URL` пуст) счётчик локальный и вопроса не возникает.

### Стоимость сида

Сид перестаёт быть чтением одного блоба и становится `SELECT` на N строк со
сборкой JSON.

**Замерено** (2026-07-21, локальный Postgres 18, freedraw по 150 точек):

| элементов | сид | сборка |
|---|---|---|
| 500 | 1.5 МБ | 80 мс |
| 1000 | 3 МБ | 156 мс |
| 2000 | 6 МБ | 314 мс |
| 5000 | 15 МБ | ~900 мс |

Сборка линейна, ~0.16 мс на элемент; порог 300 мс приходится на ~2000
элементов. Само по себе терпимо.

**Главное не в этом.** Замер вскрыл то, чего дизайн не учёл: сид перестал
сжиматься на пути из БД. Старая колонка `snapshot` — bytea+gzip, и те же
данные ехали из Supabase как ~500 КБ. Поэлементная таблица отдаёт сырой jsonb:
на той же доске это 3 МБ, в шесть раз больше по сети между Railway и Supabase.

Смягчает то, что вторая половина пути (сервер → браузер) сжимается
`permessage-deflate`, включённым в фазе B. Не сжимается только участок
Postgres → Go.

На текущих досках (~1000 элементов) открытие обойдётся в доли секунды — не
блокер выката. Но запас меньше, чем казалось, и запасное решение — последний
дамп из `board_page_snapshots` (gzip) плюс дельта по `updated_at` —
понадобится раньше: не «если упрёмся», а на первой доске вдвое крупнее
сегодняшних.

### Что уходит

- `POST /public/board/pages/:pageId/snapshot` — сначала меняет семантику на
  merge, затем удаляется совсем.
- `board_pages.snapshot` перестаёт быть источником истины; остаётся как
  периодический бэкап (см. ниже).
- Клиентские `serializeSnapshot` / `compactTombstones` — вместе со снятием
  `/snapshot` на последнем шаге выката, не раньше: пока роут жив, старые вкладки
  им пользуются. Чистка tombstones переезжает на сервер.
- Карта `files` в теле снапшота: клиент перестаёт слать её целиком, сервер
  дописывает запись при загрузке файла и отдаёт карту в сиде.

### История и чистка

- Раз в ~10 минут активная страница дампится в `board_page_snapshots
  (page_id, snapshot, created_at)`; хранение 7 дней. Назначение — откат после
  инцидента, не загрузка доски. Дамп делает инстанс, у которого есть клиенты
  этой страницы; при нескольких инстансах возможен дубль — он безвреден (лишняя
  строка истории), координация не нужна. Та же фоновая задача удаляет дампы
  старше 7 дней и tombstones старше 24 часов.
- Фоновая задача удаляет tombstones старше 24 часов (`isDeleted` + `updated_at`).
  TTL сохраняется прежним: за сутки клиент с устаревшей локальной сценой до
  реконнекта не доживает, воскрешать удалённое некому.

## Плавность

Три меры, ортогональные выбору архитектуры.

**Округление координат на WS.** Сейчас `roundFloats` применяется только в
`serializeSnapshot`; `flushUpdate` шлёт полные float64 — 40 байт на точку вместо
14. Ввести `serializeUpdate` рядом с `serializeSnapshot`, чтобы оба пути
сериализации лежали в одном месте. Безопасно: reconcile сравнивает
`version`/`versionNonce`, округление их не меняет (целые). Выигрыш ~×3.

**`permessage-deflate` на WS.** `EnableCompression: true` в `websocket.Upgrader`
(сейчас выключено). Gorilla сжимает каждое сообщение независимо, но массив из
сотен близких чисел жмётся хорошо. Выигрыш ~×3-4.

**Частота для растущего элемента.** Штрих в процессе рисования не обязан
обновляться 10 раз в секунду.

Штрих в 500 точек за 3 секунды: ~300 КБ сейчас → ~105 КБ после округления →
~30 КБ после deflate.

**Отложено: дельты точек.** Дали бы ещё ~×4 (до ~7 КБ), но требуют, чтобы сервер
понимал внутренности freedraw — а он теперь пишет в БД. Если понадобится,
делать через разделение каналов: живой штрих — эфемерный поток, который сервер
пересылает не глядя и не пишет; авторитетный полный элемент — отдельное
сообщение на завершении штриха. Тогда рассинхрон самоисправляется финальным
полным апдейтом.

## Инфраструктура

Redis на Railway (поставлен, `REDIS_URL` в env), приватная сеть, клиент
`redis/go-redis/v9`.

`LISTEN/NOTIFY` для рисования не годится: лимит payload 8000 байт (округлённый
штрих в 500 точек ~7 КБ — половина сообщений упрётся), каждое сообщение
становится запросом в БД (~500/с на 50 досках), и Postgres находится в другой
сети — десятки миллисекунд в горячем пути. Существующее применение
`LISTEN/NOTIFY` (события «PDF отрендерился») остаётся без изменений.

При пустом `REDIS_URL` работаем без Redis: один инстанс, локальный счётчик seq.
Это dev-режим и валидный однонстансный прод.

## Миграция и порядок выката

Разовый переезд данных (12 страниц) и zero-downtime деплои — разные задачи.
Переезд делается в окно без уроков; zero-downtime получается из архитектуры,
потому что состояние живёт в Postgres и Redis.

**Бэкфилл-скрипт** проходит по `board_pages`, распаковывает gzip, парсит
`elements` — вставляет строки, и `files` — пишет в новую колонку; одна
транзакция на страницу, `ON CONFLICT DO NOTHING`, выставляет
`elements_migrated_at`. Страница без `files` в старом снапшоте получает `{}`.

**Ленивый импорт** в `ServeWS` как страховка: страница без
`elements_migrated_at` переезжает при первом открытии.

Признаком «уже мигрировали» служит именно флаг, а не наличие строк в
`board_elements`: через сутки чистка tombstones обнулит полностью очищенную
доску, и импорт по признаку «нет строк» воскресил бы старый снапшот.

**Совместимость во время выката.** Открытые вкладки со старым JS продолжат слать
`POST /snapshot`. Роут остаётся, но меняет семантику с «перезаписать» на
«слить»: полная сцена мержится поэлементно тем же UPSERT'ом, `files` — через
`||`. Побочный эффект —
старый клиент со вчерашним багом становится безвреден: merge не удаляет то, чего
нет в присланном. Роут снимается через неделю.

**Порядок:**

1. миграция схемы (`board_elements`, `elements_migrated_at`, `files`) — обратно
   совместимо;
2. бэкфилл-скрипт + верификатор — в окно без уроков;
3. деплой сервера (пишет элементы, `/snapshot` → merge, флаш на shutdown);
4. деплой фронта (округление, throttle, seq-ресинк);
5. Redis pub/sub и seq — включается вторым инстансом;
6. через неделю после шага 4 — снятие `/snapshot` и мёртвого кода.

Шаги 1-3 откатываются безопасно: старый сервер продолжит работать со
`snapshot`, который мы не трогаем.

### Фазы

Шаги режутся на три части, и первые две ценны сами по себе.

**A (шаги 1-3).** Поэлементная модель. Закрывает два тупика из трёх: стирание
доски становится невозможным структурно, стоимость записи — пропорциональной
изменению. Работает на одном инстансе, Redis не нужен.

**B (шаг 4).** Плавность: округление, deflate, throttle. Ортогонально A,
выкатывается следом.

**C (шаг 5).** Redis, seq, ресинк. Нужна, когда одного инстанса перестаёт
хватать — то есть ради rolling deploy, а не ради нагрузки: 150 WS-соединений
один Go-процесс держит не замечая. Пока фаза не выкачена, `REDIS_URL` пуст и
работает однонстансный режим, описанный выше.

Резать так можно потому, что многоинстансность в дизайне и так опциональна.
Собирать всё одним куском — значит откладывать починку потери данных до
готовности Redis-слоя, который к этой потере отношения не имеет.

### Предусловие фазы C

`runMigrations` в `main.go` гоняет goose без блокировки — там же и висит
комментарий, что при втором `ROLE=api` два старта погонятся. Фаза C ровно этот
второй инстанс и вводит. Значит `goose.WithLock` (advisory lock на время
миграции) — часть шага 5, иначе первый же rolling deploy устроит гонку двух
мигрантов на одной схеме.

## Ошибки и деградация

Принцип: система деградирует, а не падает — но никогда молча.

**Redis недоступен.** Клиенты одного инстанса продолжают видеть друг друга,
запись в БД идёт. Ломается связь между инстансами. Сервер помечает pub/sub
мёртвым и шлёт клиентам флаг → баннер «Совместный режим ограничен, изменения
сохраняются» + лог.

**БД тормозит.** Запись вне горячего пути, буфер UPSERT'ов. Батчинг раз в
секунду естественно схлопывает промежуточные версии растущего штриха. При
переполнении буфера — существующий `saveFailed` → баннер «Доска не сохраняется».

**Деплой.** Буфер флашится в shutdown-пути, до `srv.Shutdown`. Требование
«потеря нескольких секунд допустима» относится к сбою, не к штатному рестарту:
деплоев будет много, и каждый не должен откусывать последнюю секунду рисования.
Флаш идёт после `bgCancel()`, но с собственным контекстом — отменённый
контекст записи не сделает.

Там же клиентам уходит close-frame, а не разрыв соединения: браузер отличает
штатное закрытие от обрыва и переподключается сразу, без backoff.

**Клиент разъехался по seq.** Дырка (`ждал 42, пришёл 44`) → `resync` → полный
снапшот с актуальным seq. Не чаще раза в 5 секунд на клиента, иначе флапающая
сеть устроит шторм.

**Обрыв в середине рисования.** Механизм не меняется: сид переставляет
`versionsRef` на то, что знает сервер, следом `flushUpdate` отправляет
расхождения. Меняется только источник сида.

**Мусор от клиента.** Валидация каждого элемента: `id` — непустая строка,
`version` — неотрицательное целое, `versionNonce` — число; лимит на число
элементов в сообщении. Невалидное сообщение отбрасывается целиком с логом,
соединение не рвём. Граница доверия сместилась вместе с ролью сервера: он
перешёл из ретранслятора в хранилище.

## Тестирование

Инфраструктура: отдельный dev-проект Supabase, `TEST_DB_URL`; тесты с БД
пропускаются, если переменная не задана. Заодно снимает риск «`make run` бьёт в
прод».

**Приоритет №1 — правило слияния**, четыре кейса из раздела «Ключевое
наблюдение». Единственное место, где расхождение с клиентом даёт неотлаживаемые
баги.

**Go:** импорт снапшота (gzip → элементы **и `files`**, идемпотентность,
выставление флага); валидация входящих элементов; сборка сида из
`board_elements` — вместе с `files`, иначе тест пройдёт на доске без картинок и
пропустит ровно ту регрессию, ради которой колонка заведена; флаш буфера при
отмене контекста записывает всё накопленное.

**Frontend (node:test):** `serializeUpdate` округляет координаты и не трогает
`version`/`versionNonce`/`seed`; детект дырки в seq → запрос ресинка.

**Верификатор миграции:** сравнение **множества id** старого снапшота и
`board_elements` по каждой странице, плюс множества ключей `files`. Не
количества — совпадение счётчиков при разном составе возможно.

**Замер:** сборка сида на странице в 5000 элементов (см. «Стоимость сида»).
Делается до шага 3 и определяет, останется ли сид прямым `SELECT`.

**Smoke руками:** два браузера; деплой во время урока; Redis выключен → баннер и
целостность данных; открытие мигрированной доски; обрыв сети посреди штриха;
**доска с картинкой и импортированной PDF-страницей после бэкфилла** — самая
дешёвая проверка того, что `files` доехали.

## Что не делаем и почему

- **CRDT / Yjs.** Выигрывает при оффлайн-слиянии, посимвольном соредактировании
  одного текста и десятках редакторов. Ничего из этого нет: репетитор и один-три
  ученика рисуют разные элементы, где LWW-per-element и CRDT дают одинаковый
  результат. Excalidraw официально на Yjs не работает — интеграции сторонние.
- **Операционный лог с компакцией.** Одна строка на элемент проще и достаточна
  на горизонте задачи.
- **Дельты точек freedraw.** Отложены, решение записано выше.
- **Sticky-роутинг по board_id.** Railway не даёт L7-роутинга по хешу; проксирование
  WS между инстансами сложнее Redis pub/sub.

## Открытые вопросы

Нет. Одно решение отложено до замера: остаётся ли сид прямым `SELECT` или
собирается из дампа с дельтой. Оба варианта описаны, выбор делает цифра, а не
обсуждение.
