# Аккаунты учеников и вход в урок — v1 (фундамент)

**Дата:** 2026-07-10
**Статус:** одобрено к планированию
**Объём:** v1 = фундамент (аккаунт + приглашение + вход + сессия) + вход в урок.
Расписание/задания/история и оплаты учеником — отдельными спеками позже.

## Проблема

Сейчас `students` — это записи, которые заводит репетитор (`tutor_id` FK,
каскадное удаление). У ученика нет собственного входа: в звонок/на доску он
попадает либо анонимно по публичной ссылке (`guest-token`), либо репетитор
пускает его сам. Нужно дать ученику самостоятельный аккаунт: регистрация по
приглашению, вход по телефону **или** логину + паролю, и вход в свои уроки
(звонок + доска) под именем.

## Ключевые решения (зафиксированы на брейншторме)

1. **Связь аккаунта с записью — по приглашению репетитора.** Один аккаунт =
   одна запись у одного репетитора. Отдельная таблица аккаунтов не нужна —
   расширяем `students`; invite-модель + существующий CASCADE делают связь
   бесплатной.
2. **Вход по телефону ИЛИ логину** (любой из двух), оба уникальны среди реальных
   аккаунтов.
3. **Уроки становятся приватными.** Анонимный `guest-token` для запланированных
   уроков убирается: войти может только залогиненный записанный ученик.
   Quick-rooms остаются анонимными (это ad-hoc комнаты без учеников).

## Архитектура

### 1. Данные — миграция `020_student_accounts.sql`

Расширяем `students` (не заводим новую таблицу):

```sql
ALTER TABLE students
  ADD COLUMN username          TEXT,
  ADD COLUMN password_hash     TEXT,
  ADD COLUMN invite_token      UUID,
  ADD COLUMN invite_expires_at TIMESTAMPTZ;

-- Уникальность только среди карточек, у которых реально есть аккаунт.
CREATE UNIQUE INDEX students_username_key
  ON students (username) WHERE password_hash IS NOT NULL;
CREATE UNIQUE INDEX students_phone_account_key
  ON students (phone)    WHERE password_hash IS NOT NULL;
-- Поиск приглашения по токену.
CREATE UNIQUE INDEX students_invite_token_key
  ON students (invite_token) WHERE invite_token IS NOT NULL;
```

`username`/`password_hash` nullable: не у каждой карточки есть аккаунт (репетитор
завёл, но не пригласил / ученик не принял).

### 2. Аутентификация и JWT

**Поправка безопасности (обязательна).** JWT-секрет общий с репетиторами. Токен
ученика (`id`=studentID) без защиты пройдёт сквозь репетиторский `middleware.Auth`
как валидный принципал (studentID подставится как tutorID). Чиним обе стороны
через claim роли:

- Токен ученика несёт `role:"student"`; токен репетитора — роли нет (старые
  репетиторские куки остаются валидны).
- `middleware.AuthStudent` — требует `role=student`, кладёт `studentID` в контекст.
- `middleware.Auth` (репетитор) — **отклоняет** токен с `role=student`; отсутствие
  роли трактует как репетитора.

Refresh-токены и cookie-механизм переиспользуем (при необходимости refresh-запись
различает актора). Access-токен ученика — тот же HS256, claims `id`+`role`.

**Эндпоинты (сторона ученика):**

| Метод | Путь | Назначение |
|-------|------|------------|
| POST | `/student/auth/accept-invite` | принять приглашение: `{token, username, password}` → создать аккаунт на существующей записи, выдать сессию |
| POST | `/student/auth/login` | `{identifier, password}` (identifier = телефон или username) |
| POST | `/student/auth/refresh` | обновить access-токен |
| POST | `/student/auth/logout` | сбросить сессию |

`accept-invite` находит запись по `invite_token` (валиден и не истёк), проверяет
уникальность username/phone среди аккаунтов, ставит `password_hash`, чистит
`invite_token`.

### 3. Приглашение (сторона репетитора)

| Метод | Путь | Назначение |
|-------|------|------------|
| POST | `/students/:id/invite` | tutor-authed: генерит `invite_token` + `invite_expires_at`, возвращает ссылку |

Тот же паттерн, что quick-room ссылки. Повторный вызов перегенерирует токен.

### 4. Вход в урок (security-критичное ядро)

Урок висит на курсе **двумя** способами, проверка записи должна учитывать оба:
- индивидуальный курс: `courses.student_id = studentID`;
- групповой курс (`courses.student_id IS NULL`): строка в
  `course_enrollments (course_id, student_id)`.

**Звонок:**

| Метод | Путь | Назначение |
|-------|------|------------|
| POST | `/student/lessons/:id/room-token` | student-authed: проверка записи (оба пути) → LiveKit-токен, identity `student-<studentID>` |

**Доска — ноль изменений в WS-хабе.** Залогиненному записанному ученику отдаём
существующий invite-токен доски этого урока через authed-эндпоинт
(`GET /student/lessons/:id/board-token` → проверка записи → invite доски). Дальше
работает текущий `JoinByInvite`/`authorizeWS`.

```
// ponytail: invite доски — post-auth bearer (выдаётся только после проверки
// записи). Если важна защита от утечки UUID — добавить ветку student-JWT в
// authorizeWS. Пока переиспользуем существующий invite-путь (ноль изменений в WS).
```

**Убираем:** `GET /public/lessons/:id/guest-token` (и связанный публичный вход на
запланированный урок). Quick-room публичные эндпоинты (`/public/quick/...`) —
не трогаем.

### 5. Фронтенд (v1)

- `(student-auth)`: страницы «принять приглашение» и «вход» (телефон/логин).
- Кабинет ученика: список ближайших уроков + активная кнопка «Войти», ведущая в
  тот же звонок+доску, что у репетитора, но под токеном ученика.
- Переиспользуем существующие компоненты звонка/доски; отличие — источник токена.

## Известные границы (осознанные, ponytail)

- **Один телефон — один аккаунт.** Человек, занимающийся у двух репетиторов,
  получит две записи → два приглашения → второй раз тот же телефон не пройдёт
  (частичный unique). Прямое следствие «одна запись на репетитора» (принято с
  «пока»). Снимается только переходом к marketplace-модели — вне v1.
- **Уроки приватны.** Ученик без принятого приглашения на урок не попадёт;
  репетитор обязан пригласить заранее. Для разовых/пробных учеников остаётся
  quick-room.
- **Вне v1:** расписание, задания, история/прогресс, оплаты учеником — отдельные
  спеки.

## Тестирование

- middleware: student-токен отклоняется репетиторским `Auth`; репетиторский
  токен отклоняется `AuthStudent`; токен без роли = репетитор.
- accept-invite: истёкший/неизвестный токен → отказ; дубль username/phone → отказ.
- login: телефон и username оба работают; неверный пароль → отказ.
- room-token: не записанный ученик → 403; записанный по `student_id` → ok;
  записанный по `course_enrollments` → ok.
- guest-token запланированного урока → 404/удалён; quick-room guest-token → жив.
