## 1. Что установлено

### 1.1 Подтверждённые дефекты

**A. `scope=all` уничтожает будущие вхождения вместо переноса.** Живёт в проде **для
событий прямо сейчас** — `EventQuickPopover` показывает кнопку «Все». Для уроков
недостижимо только потому, что до `scope` не доезжает интерфейс (дефект C).

`service/recurrence.go:120` рано выходит, когда граница уже дальше горизонта:

```go
if !rule.MaterializedUntil.Before(horizon) {
    return 0, nil // горизонт уже дальше — двигать назад нечего
}
```

`UpdateTiming` (`repository/recurrence.go:117`) меняет только `time_local` и
`duration_minutes`, оставляя `materialized_until` на горизонте. Дальше
`DeleteFutureByRule` сносит будущее, а `Materialize` считает
`Occurrences(rule, materialized_until, horizon)` — то есть полоску в несколько дней
между старым и новым горизонтом. Окно между «сегодня» и старым горизонтом остаётся
пустым навсегда.

`scope=following` не сломан ровно потому, что `Split` (`repository/recurrence.go:92`)
явно ставит новому правилу `materialized_until = $2::date`.

**B. Серия не умеет менять день недели.** `UpdateTiming` не пишет `byweekday`,
`Split` копирует его дословно, `occurrence_date` правимого вхождения не двигается
никогда. Пока интерфейс мёртв, это не видно; в момент починки дефекта C сценарий
«перенести группу с понедельника на вторник → изменить все» становится доступен и
даёт рассогласованные данные: правило по-прежнему weekly-Monday, один урок во
вторник с понедельничным `occurrence_date`, всё будущее снова по понедельникам.
**Чинится в одном коммите с A, до C.**

**C. `rule_id` не селектится — весь серийный UI мёртв.** Мест не три, как считала
исходная спека, а четыре: `repository/lesson.go` — `GetByCourse` (:57),
`GetByCoursePaged` (:77), `GetByID` (:105), `GetByPeriod` (:248). `GetByIDForTutor`
(:154) поля селектит, поэтому серверная логика отрабатывает, когда `scope` до неё
доезжает.

Следствие: `models.Lesson.RuleID` всегда `nil` → `omitempty` выбрасывает поле из
JSON → на фронте обе точки входа в серийную правку гейтятся на `undefined`
(`courses/[id]/page.tsx:154` и `:181`), `RecurrenceScopeDialog` не открывается
никогда.

Второе следствие, менее заметное: «удалить урок» серии со страницы курса уходит без
`scope`, сервер подставляет `one`, и `service/lesson.go:333` вызывает `Cancel`.
Строка **остаётся** как `cancelled, is_override = TRUE` — пользователь видит, что
урок не удалился.

**D. Архивация курса не убирает будущие уроки.** `service/course.go:78` — это
`UPDATE courses SET is_active = FALSE` и больше ничего. `GetCalendar`
(`repository/lesson.go:194`) фильтрует только по `tutor_id`. Правило курса остаётся
живым и продолжает материализоваться.

**E. Попап урока в календаре не умеет ни времени, ни удаления, ни серии.**
`calendar/page.tsx:238` собирает `QuickLesson` и **выбрасывает `rule_id`**, хотя API
его отдаёт (`CalendarLesson.rule_id`, `repository/lesson.go:219`).
`LessonQuickPopover` не имеет ни полей времени, ни кнопки удаления.

### 1.2 Дефекты, которых в исходной спеке не было

**F. Нет крэш-безопасности.** `UpdateTiming → Update → DeleteFutureByRule →
Materialize` — четыре отдельных запроса без транзакции. Обрыв между третьим и
четвёртым (деплой, таймаут пула, OOM) оставляет будущее удалённым, а
`materialized_until` — на горизонте. Ночная джоба такое правило не подберёт:
`DueForMaterialization` смотрит `materialized_until < horizon`. То есть дефект A
воспроизводится навсегда, но уже без ошибки в коде.

**G. Дублирование — причина того, что A существует дважды.**
`service/lesson.go:updateSeries` (:256) и `service/event.go:applyToSeries` (:112) —
один алгоритм, набранный два раза. Инструкция «починить обе копии» сохраняет
фабрику багов, а логика смены дня недели (дефект B) — самая тонкая часть задачи,
которую нельзя писать дважды.

**H. `service/lesson.go:294` теряет инвалидацию кеша.** Ошибка `Materialize`
возвращает управление до `globalCalendarCache.Invalidate(tutorID)`, и календарь
отдаёт устаревшие уроки, пока не истечёт TTL.

### 1.3 Опровергнуто: «правило переживает удаление уроков и возвращает их»

Исходная спека описывала механизм: `DeleteByCourse` не трогает
`recurrence_rules`, осиротевшее правило остаётся в `DueForMaterialization`, ночная
джоба возвращает уроки. **Этот механизм невозможен.**

`InsertOccurrences` (`repository/recurrence.go:137`) берёт шаблон нового вхождения из
живого урока того же правила, через внутренний `JOIN LATERAL`:

```sql
JOIN LATERAL (
    SELECT course_id, duration_minutes, notes FROM lessons
    WHERE rule_id = $1::uuid ORDER BY scheduled_at LIMIT 1
) t ON TRUE
```

`DeleteByCourse` сносит **все** уроки курса — FK у `attendance` (`002_calendar.sql`)
и `lesson_tasks` (`022_lesson_tasks.sql`) объявлены `ON DELETE CASCADE`, так что
удаление проходит целиком. Шаблона не остаётся, LATERAL возвращает ноль строк,
вставлять нечего. Других путей вставки урока в коде нет: `INSERT INTO lessons`
встречается ровно дважды — `lessonRepository.Create` и `InsertOccurrences`.

**Срез прода на 2026-09-06 это подтверждает.**

| факт | значение |
|---|---|
| правил всего | 34, все `weekly` с `interval_n = 1` |
| бессрочных (`ends_on IS NULL`) | 3, все на активных курсах |
| правил-сирот | 1 (`78ec439d`, weekly `{вт,чт}` 19:30, `starts_on 2026-06-23`) |
| уроков, созданных этой сиротой | **0** |
| `is_override` всего / в будущем | 167 / 26 |
| будущих уроков архивированных курсов | 52 на одном курсе |

Курс, на котором наблюдался симптом (`1e1db4a8`, «Английский», группа) —
**архивирован** (`is_active = false`) и держит 51 будущий `scheduled` урок до
2027-03-04 плюс 12 завершённых. Правило `a4ec96dd`: weekly `{2,4}` 20:30
Asia/Almaty, `ends_on 2027-03-04`, `materialized_until 2027-03-05`. Уроки не
возвращались — их никогда не удаляли. **Это дефект D, а не отдельный баг.**

Что остаётся от исходного бага 3: `DeleteByCourse` действительно плодит
правила-сироты. Это течь (мусорная строка, ежедневный пустой скан джобы), а не
источник воскрешения. Чинится в §4.

### 1.4 Отклонено: ремонт `is_override`

Исходная спека называла массовую простановку `is_override` «побочным эффектом,
портящим данные», и предлагала искать пострадавших через
`SELECT * FROM lessons WHERE is_override`. Ремонта не будет, и вот почему.

Из 167 флагов 152 поставила миграция 036 — она метила всё, что не легло в
восстановленную форму серии. Из 26 будущих флагов ровно 2 стоят на уроках, лежащих
по расписанию правила, и один из них — корректный тумбстоун отменённого вхождения
(`Cancel` ставит `is_override` намеренно), второй объясняется правкой одной только
длительности. Остальные 24 действительно сдвинуты относительно правила.

Отличить артефакт миграции, законный drag-and-drop и последствие дефекта C
постфактум нечем — все три ставят один и тот же флаг. Массовое снятие сломает
больше, чем починит.

## 2. Ядро: `RecurrenceService.Retime`

Вся арифметика правила и весь порядок операций собираются в один метод. Это ответ
на дефект G: смена дня недели, откат watermark и последовательность
«удалить → переставить → материализовать» существуют в единственном экземпляре и
покрываются одним набором тестов.

```go
// Retime переносит серию, взяв за образец вхождение occurrenceID.
//
// Вызывающий обязан обновить свою строку (время, заметки, статус) ДО вызова:
// Retime переставляет только rule_id/occurrence_date и пересобирает будущее.
//
// scope = following — правило разрезается, вхождение уходит в новую ветку;
//         all       — правится правило целиком, прошедшие вхождения не трогаются.
// scope = one сюда не приходит: одиночная правка правила не касается.
//
// Правило принимается готовым, а не читается по id: вызывающий всё равно держит
// его ради NormalizeSeriesStart (§2.2), и второе чтение было бы лишним.
Retime(ctx context.Context, rule models.RecurrenceRule, occurrenceID string,
       from time.Time, newStart time.Time, duration int, scope string) error
```

Порядок внутри — обязательный, не косметический:

| шаг | действие | зачем именно здесь |
|---|---|---|
| 1 | `NormalizeSeriesStart` (§2.2) → `newDate`, `timeLocal`, новый день недели | правило хранит стенные часы, запрос приходит в UTC |
| 2 | пересчёт `byweekday` (см. §2.1) | |
| 3 | `cut := min(from, newDate)` | дата, с которой серия пересобирается |
| 4a | `following`: `Split(ruleID, cut, timeLocal, duration, byweekday)` | `Split` уже ставит `materialized_until = cut` |
| 4b | `all`: `UpdateTiming(...)`, **сразу за ним** `SetMaterializedUntil(ruleID, cut)` | откат watermark **до** разрушения — см. §2.3 |
| 5 | `DeleteFutureByRule(`**исходное**` правило, cut − 1, except = occurrenceID)` | см. ниже про источник и границу |
| 6 | `ReassignToRule(occurrenceID, targetRule, newDate)` | после удаления: иначе коллизия по уникальному индексу |
| 7 | `Materialize(targetRule, now + RecurrenceHorizon)` | |

**Источник и цель — разные правила.** Чистим всегда `rule.ID`, материализуем
`targetRule`. При `scope=all` это одно и то же; при `following` целевое правило
только что создано и вхождений не имеет, а чистить надо именно старое — иначе его
будущие вхождения остаются жить параллельно новой ветке.

**Граница включительная.** Удалять надо всё начиная с `cut`, поэтому в `after`
(семантика строгого `>`) уходит `cut − 1 день`. Перенос «четверг → вторник той же
недели» под `scope=all` даёт `cut` = вторник, и старая вторничная строка того же
правила ещё существует; строгое `> cut` её бы не тронуло, и шаг 6 упёрся бы в
`idx_lessons_rule_occurrence`. При обычной смене времени `cut = from`, и под удаление
попадает только правимое вхождение — которое `exceptID` и щадит.

### 2.1 Смена дня недели: подмена своего дня

`byweekday` пересчитывается **заменой дня переносимого вхождения**, а не
объединением и не заменой всего набора:

```
правило {2,4} (вт, чт), переносим вторничное вхождение на среду
→ {3,4}      ✔ вторник ушёл, среда пришла, четверг на месте
→ {2,3,4}    ✘ серия стала трёхдневной
→ {3}        ✘ четверг потерян
```

Вырожденные случаи:

- `byweekday` пуст — `Occurrences` в этом случае берёт день недели из `starts_on`
  (`service/recurrence.go`, ветка `default: weekly`). Перед подменой набор
  материализуется: `byweekday = {isoWeekday(starts_on)}`.
- новый день уже в наборе (`{2,4}`, вторник → четверг) — набор схлопывается в `{4}`,
  серия становится однодневной. Это буквально то, о чём попросил пользователь;
  отдельной обработки нет.
- `freq != "weekly"` и дата изменилась — `ErrBadRequest` (400). У `daily` смена даты
  бессмысленна, у `monthly` день месяца выводится из `starts_on` и требует другой
  операции. В проде правил с такой частотой ноль, а фронт создаёт только `weekly`
  (`frontend/src/lib/recurrence.ts:36`).

### 2.2 Семантика даты при `scope != one`

**Серию определяет пара (день недели, время). Выбранная в форме дата служит только
источником дня недели.**

`newDate` считается как дата в той же неделе, что и `from`, но на новом дне недели.
Перенос «чт 10 сентября → чт 17 сентября» под «изменить все» — это чистая смена
времени: неделя игнорируется, `newDate = 10 сентября`. Перенос «чт 10 сентября →
ср 23 сентября» даёт `newDate = ср 9 сентября`.

Из этого следует обязательная **нормализация запроса**: перед `repo.Update`
вызывающий заменяет `req.ScheduledAt` на `newDate + timeLocal` в зоне правила. Без
неё строка урока уедет на 23 сентября, а `occurrence_date` останется 9-м — ровно тот
рассинхрон, который описан в дефекте B.

`Retime` вызывается **после** `repo.Update` (см. §2.4) и поэтому нормализовать
запрос за вызывающего не может. Нормализация выносится в свободную функцию пакета
`service`, которую зовут обе стороны — дублирования логики нет:

```go
// NormalizeSeriesStart приводит время запроса к дате, которую примет правило:
// при scope != one серию задают день недели и время, а не выбранная в форме неделя.
// Для freq != "weekly" со сменой даты возвращает ErrBadRequest (см. §2.1).
func NormalizeSeriesStart(rule models.RecurrenceRule, from, newStart time.Time) (time.Time, error)
```

`Retime` вызывает её первым делом на шаге 1 и дальше работает уже с нормализованным
временем.

### 2.3 Крэш-безопасность без транзакций

Шаг 4b ставит `materialized_until = cut` **перед** удалением на шаге 5. Инвариант:
*система никогда не выглядит завершённой, пока не завершена.*

Любой обрыв после шага 4 оставляет правило в выборке `DueForMaterialization`
(`materialized_until < horizon`), и ночная джоба (`worker/run.go:105`, раз в сутки
плюс `RunOnStart: true` на каждом редеплое) долечивает сама. Уникальный индекс
`(rule_id, occurrence_date)` вместе с `ON CONFLICT DO NOTHING` гарантирует, что
повтор не наплодит дублей.

Худший исход обрыва — правка времени не доехала до будущих вхождений; старые строки
на месте, дыры нет. Это строго лучше текущего поведения и стоит двух строк вместо
`pgx.Tx` во всех трёх репозиториях.

### 2.4 Как выглядят вызывающие

`service/lesson.go:updateSeries` целиком:

```go
func (s *lessonService) updateSeries(ctx context.Context, lesson models.Lesson,
    req models.UpdateLessonRequest, tutorID, scope string) (models.Lesson, error) {

    rule, err := s.recurrence.GetRule(ctx, *lesson.RuleID)
    if err != nil {
        return models.Lesson{}, err
    }
    // Серию задают день недели и время; выбранная неделя роли не играет.
    req.ScheduledAt, err = NormalizeSeriesStart(rule, *lesson.OccurrenceDate, req.ScheduledAt)
    if err != nil {
        return models.Lesson{}, err
    }

    updated, err := s.repo.Update(ctx, lesson.ID, req)
    if err != nil {
        return models.Lesson{}, err
    }
    if err := s.recurrence.Retime(ctx, rule, lesson.ID, *lesson.OccurrenceDate,
        req.ScheduledAt, req.DurationMinutes, scope); err != nil {
        return models.Lesson{}, err
    }
    globalCalendarCache.Invalidate(tutorID)
    return updated, nil
}
```

`service/event.go:applyToSeries` **исчезает целиком**; `eventService.Update`
получает те же четыре шага.

Порядок «своя строка → `Retime`» выбран сознательно: если `Update` прошёл, а
`Retime` упал, урок стоит на новом времени, а серия не тронута — состояние видимое,
безвредное и чинится повтором запроса. Обратный порядок оставил бы правило
перестроенным вокруг вхождения, которого там нет.

Дефект H закрывается тем же изменением: ошибка `Materialize` больше не глотается
внутри, а возвращается наверх, и `Invalidate` либо выполняется, либо запрос честно
падает.

### 2.5 Известные семантические компромиссы

Два выбора, которые сейчас нигде не зафиксированы, кроме комментариев к тестам.

**Потеря хвоста при `ends_on`.** Перенос дня недели вперёд по неделе может
укоротить ограниченную серию на одно вхождение: последнее вхождение уезжает за
`ends_on`, который остался привязан к старому ритму (`SetEndsOn`/`Split` его не
трогают, а материализация после переноса просто упирается в старую границу
раньше). В проде 31 правило из 34 имеет `ends_on`, так что это заметно, а не
теоретический край.

**Обратный охват `following`.** `cut := min(from, newDate)` (см. §2) означает, что
«это и все следующие» с переносом на более ранний день недели затрагивает
вхождение, предшествующее выбранному, — до шести дней назад. Это осознанный
размен против уникального индекса (§2, «Граница включительная»): без отката cut
назад `ReassignToRule` столкнулся бы с `idx_lessons_rule_occurrence`. Но
пользователь, нажавший «это и все следующие» на вторнике, не ожидает, что
предыдущий четверг тоже уедет в новую ветку — ярлык обещает будущее, а трогает
кусок прошлого.

## 3. Репозитории

### 3.1 `RecurrenceRepository`

Правило владеет вхождениями в обеих таблицах, поэтому методы, работающие «по
`rule_id`», делают по паре запросов — ровно как уже устроен `InsertOccurrences`, где
один INSERT попадает, а второй не находит шаблона.

| метод | изменение |
|---|---|
| `Split` | `+ byweekday []int` — пишется в новое правило вместо копирования |
| `UpdateTiming` | `+ byweekday []int` |
| `DeleteFutureByRule(ruleID, after, exceptID)` | **новый**, удаляет из `lessons` и `events` |
| `ReassignToRule(occurrenceID, ruleID, date)` | **новый**, обновляет `lessons` и `events` по `id` |

`DeleteFutureByRule` сохраняет существующие условия каждой таблицы дословно:
`lessons` — `is_override = FALSE AND status = 'scheduled'`; `events` —
`is_override = FALSE AND NOT cancelled`. Плюс `AND id <> $3` при непустом `exceptID`.

Одноимённые методы **удаляются** из `LessonRepository` (:183 области) и
`EventRepository` (:90): их последние вызовы — в `Delete` со `scope=following|all` —
переезжают на recurrence-версию с пустым `exceptID`. `ReassignToRule` удаляется
оттуда же.

### 3.2 `LessonRepository`: константа колонок

Причина, по которой поля забыли в четырёх местах, а у событий — ни в одном:
`repository/event.go:14` держит `eventColumns` одной константой, и добавление
`rule_id` в миграции 033 автоматически прошло во все выборки. У уроков SQL написан
россыпью.

```go
const lessonColumns = `l.id, l.course_id, l.scheduled_at, l.duration_minutes,
                       l.status, l.notes, l.rule_id, l.occurrence_date`

func scanLesson(row interface{ Scan(...any) error }) (models.Lesson, error)
```

Алиас `lessons l` добавляется во все четыре запроса, включая те, где джойна нет —
иначе константа не переиспользуется. Затрагиваются `GetByCourse` (:57),
`GetByCoursePaged` (:77), `GetByID` (:105), `GetByPeriod` (:248);
`GetByIDForTutor` (:154) переводится на ту же константу.

Два новых метода для §4:

```go
GetRuleIDsByCourse(ctx context.Context, courseID string) ([]string, error)
DeleteFutureByCourse(ctx context.Context, courseID, tutorID string) error
```

`DeleteFutureByCourse` берёт только `status = 'scheduled' AND scheduled_at > now()` —
завершённые, отменённые и пропущенные остаются.

## 4. Правила курса: архивация и «удалить все уроки»

Правило не связано с курсом напрямую — связь только через `lessons.rule_id`.
Поэтому оба сценария начинаются с чтения `GetRuleIDsByCourse`: после удаления уроков
связь не восстановить.

Два метода на `lessonService`, у него уже есть и `recurrence`, и `courseRepo`:

```go
// ArchiveCourseSchedule закрывает серии курса и убирает будущие уроки.
// Завершённые остаются — это обещано текстом диалога архивации.
ArchiveCourseSchedule(ctx context.Context, courseID, tutorID string) error
```

- каждому правилу `SetEndsOn(today)`, затем `DeleteFutureByCourse`;
- правило **закрывается, а не удаляется**: у прошедших уроков `rule_id` остаётся, и
  история занятий сохраняет признак серии. Из `DueForMaterialization` закрытое
  правило выпадает по `ends_on > CURRENT_DATE`.

`DeleteByCourse` (`service/lesson.go:337`) наоборот — `recurrence.DeleteRule` для
каждого найденного правила, затем `repo.DeleteByCourse`. Уроков не остаётся вовсе,
шаблона у правила нет, хранить нечего; сирот больше не появляется.

### 4.1 Проводка

`courseService` получает третьим аргументом узкий интерфейс:

```go
type courseSchedule interface {
    ArchiveCourseSchedule(ctx context.Context, courseID, tutorID string) error
}
```

`courseService.Delete` (`service/course.go:78`) после успешного
`repo.Delete` вызывает `schedule.ArchiveCourseSchedule`.

В `router/router.go` строка создания `courseService` (:55) переезжает ниже
`lessonService` (:58). Цикла зависимостей нет: `lessonService` зависит от
`courseRepo`, а не от `courseService`; `onboardingService` создаётся позже обоих.

### 4.2 Восстановление курса

`Restore` возвращает курс **без расписания** — правила закрыты, будущие уроки
удалены безвозвратно. Завершённые уроки, посещаемость, платежи и доски на месте.
Серию заводят заново.

Соответственно текст диалога архивации (`courses/page.tsx:140`) переписывается на
честный: «Завершённые уроки останутся в календаре, будущие будут удалены».

Фильтр `is_active` в `GetCalendar` **не добавляется** — он спрятал бы и завершённые
уроки, что противоречит обещанию диалога.

## 6. Тесты

### 6.1 Юнит (`service/`, моки)

Новый файл `service/retime_test.go`:

- четыре комбинации `{all, following} × {со сменой дня, без смены}`;
- **порядок вызовов**: `SetMaterializedUntil(cut)` происходит до
  `DeleteFutureByRule`. Именно это не ловилось раньше — используйте
  `mock.InOrder` или счётчик вызовов, иначе тест снова окажется зелёным на сломанном
  коде;
- подмена дня: `{2,4}`, вторник → среда даёт `{3,4}`; пустой `byweekday`
  материализуется из `starts_on`; новый день уже в наборе схлопывает его;
- `freq = "monthly"` со сменой даты → `ErrBadRequest`;
- `NormalizeSeriesStart`: «чт 10.09 → чт 17.09» даёт 10.09 с новым временем;
  «чт 10.09 → ср 23.09» даёт ср 09.09.

`service/scope_test.go` переписывается под новые сигнатуры. Мок
`mockRecurrenceRepo` (`service/materialize_test.go:15`, дополняется в
`scope_test.go:31`) и моки в `handlers/mocks_test.go` синхронизируются с
интерфейсами — **рассинхрон ломает компиляцию тестов, это главный footgun проекта**.

### 6.2 Интеграционные (`make test-integration`, тег `integration`)

Дефект A на моках не воспроизводится в принципе — фикстура правила создаётся с
нулевым `MaterializedUntil`, и ранний выход `Materialize` не срабатывает. Без живой
БД эти сценарии не проверить:

1. серия из 10 недельных уроков, «изменить все» на пятом → первые четыре на старом
   времени, с пятого по десятый на новом, ни одного потерянного, ни одного лишнего;
2. то же для события;
3. перенос серии со вторника на среду под «изменить все» → все будущие в среду,
   прошедшие остались во вторник, `byweekday` правила обновлён;
4. «это и все следующие» на удаление → текущее вхождение `cancelled` (не удалено),
   последующие удалены, правило закрыто, `ExtendAll` их не возвращает;
5. вручную перенесённый урок (`is_override`) переживает обе операции;
6. архивация курса → будущих уроков нет, завершённые на месте, `ExtendAll` новых не
   создаёт;
7. «удалить все уроки» → правил курса не осталось, `ExtendAll` ничего не создаёт.

`.env` смотрит в прод-Supabase.

## 9. Что проверить руками после деплоя

- серия из 10 недельных, «изменить все» на пятом — четыре старых, шесть новых;
- то же через `EventQuickPopover`;

- «это и все следующие» на удаление, затем редеплой (`RunOnStart: true`) — уроки не
  вернулись;
- «удалить все уроки», затем редеплой — уроки не вернулись;
- архивированный курс: будущих уроков в календаре нет, завершённые на месте;
- попап урока в календаре: смена времени, удаление, вопрос об области у серии;
- перетаскивание урока мышью по-прежнему не спрашивает область.
